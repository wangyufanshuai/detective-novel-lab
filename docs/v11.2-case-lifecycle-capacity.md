# v11.2 case lifecycle and campaign capacity

The persistent town now distinguishes the event that makes a case playable from the six-stage chain that prepares it. A chain records one stable `triggeredEventId` and one `CaseTriggerKind`; a `fatal` trigger consumes the victim's living state, while a `nonfatal_incident` keeps both actors alive and exposes incident-specific evidence. The extraction view copies the source trigger and never fabricates a death scene for an incident.

That contract is now protected against two false improvements:

- a candidate id may contain the current tick and ranking position, so it cannot be used as case identity;
- a historical evidence index may retain the source chain without becoming the social-pressure input for the next tick.

The high-capacity campaign policy is `source-signaled`: it creates a fatal trigger only when the executed source chain contains an explicit fatal signal (`fatal_signal`, `lethal_escalation`, `weapon_use`, `attack`, or `murder`). Existing runtimes and short smoke tests retain the `legacy-fatal` policy for compatibility. This keeps event-kind selection deterministic and auditable; it never alternates kinds from a trigger count or campaign rank.

## Required lifecycle split

Before changing the campaign target, introduce a typed trigger profile with at least:

1. `fatal`: a death event consumes the victim's living state and exposes a death-scene evidence contract.
2. `nonfatal_incident`: a crime or civic incident keeps the actors alive and exposes an incident-specific evidence contract.
3. `population_flow`: an arrival or replacement event adds a new NPC only with a deterministic provenance chain, schedule, relationships, and replay identity.

Each trigger record must carry the trigger kind, source event id, source candidate id, and the lifecycle effect. A case id must remain a function of the stable trigger identity and actor pair; it must never be a function of the extraction tick alone.

## Implementation order

1. Keep the trigger-kind type and migration defaults for existing fatal records.
2. Keep the nonfatal incident event and dedicated extraction adapter on the same six-stage provenance contract, without synthesizing a death event.
3. Add deterministic population-flow records only after the replay and save/load contract can restore the newcomer identically. The explicit `applyPopulationFlow` adapter and persisted ledger now satisfy this gate; automatic tick cadence remains a separate integration decision.
4. Extend candidate validation, case graphs, the agent-control API, and the room projection so the trigger kind is visible in public-safe summaries.
5. Re-run the 1000-tick and 5000-tick gates. The high-capacity run now uses an eight-chain ledger budget, a five-tick source-signaled refresh cadence, a bounded recent exclusion window, and indexed event-time/memory lookups. These are performance boundaries for the high-capacity policy; the legacy path keeps its original cadence and event history.

## Current engineering receipt

The completed 5,000-tick `campaign-validation` artifact records 30/30 unique cases, 30/30 complete evidence graphs, zero evidence-graph warnings, 21 distinct case types, 100% later-case influence, and zero candidate repeats. The saved receipt took 52.3 seconds; the `case-chain` phase consumed 4.97 seconds (9.5% of the run, below the 42% gate). An earlier clean replay of the same source-signaled run completed in 37.9 seconds (10.9% case-chain), so the runtime difference is execution variance rather than a changed deterministic result. Both receipts carry `fnv1a-47c2f724`. The existing 100-tick legacy-fatal run still reports `fnv1a-3374875d`.

The receipt proves the engine candidate gate and replay/evidence contracts. It does not approve the 3D room's Function/Form/Runtime art gates, prove licensed external assets, or replace human comprehension and art-direction review.

The population-flow contract is covered by `npm run test:population-flow`. It creates a source-backed arrival with deterministic NPC identity, schedule, relationships, memory, and `causedByEventIds`, then proves same-snapshot replay, normalized save/load replay, and idempotent duplicate suppression. This is an explicit engine adapter receipt; it does not yet change the 5,000-tick campaign hash because population flow is not automatically scheduled in the legacy or source-signaled tick loop.

## Stop conditions

- Do not call the high-capacity result a production release until the same receipt is reproduced for the intended release commit and the remaining rights, visual, device, and human gates are closed.
- Do not count a repeated death event, a resurrected NPC without a population provenance record, or a case whose extraction adapter fabricates a death scene.
- Do not bind the 3D room to a case type that is not present in the source event and public-safe case summary.

This document is a design contract and implementation queue. Nonfatal incidents are implemented behind the explicit source-signaled policy; population flow and its save/load provenance contract are implemented as an explicit adapter, and the default-off source/age/cadence/cap policy is covered by a 100-tick contract. The 1,000/5,000-tick population fairness receipts remain pending.
