# v10.0 Save and Migration Policy

v10.0 freezes the current storage authorities. It adds no SQLite table, column, endpoint, content schema, public schema, or runtime format version. The repository schema remains version 4 and the browser Continue pointer remains `formatVersion: 1` under `detective-town-launch-v1`.

## Compatibility contract

- **Legacy browser pointer:** a structurally safe `{ worldId, sessionId }` value is migrated to pointer format 1. Unsafe/path-like values are rejected.
- **Current pointer:** format 1 loads without reinterpretation. A pointer is only persisted after a successful Campaign extraction.
- **Corrupt pointer:** invalid JSON or invalid fields are cleared locally; the Campaign Front Door stays open and offers a clean start.
- **Stale pointer:** a structurally valid pointer to a missing world/session is not treated as success. The pointer is cleared only after the Server proves it stale.
- **Legacy Persistent Town JSON:** `normalizePersistentTownRuntime` repairs absent collections and bounded scalar fields without advancing a tick, generating an event, or mutating the loaded world.
- **Current/forward JSON:** unknown top-level and nested optional fields are preserved through normalization. This permits a newer save to survive an older compatible reader when the unknown data is not authoritative for that reader.
- **Corrupt runtime JSON:** invalid statuses, counts, collections, and world bindings fall back to deterministic safe defaults. Raw parse/storage failures remain failed loads and never create a false Continue state.

The tracked fixture [save-compatibility-v10.json](../tests/fixtures/save-compatibility-v10.json) covers legacy, current, corrupt, and stale pointer/runtime shapes. `npm.cmd run test:save-recovery` proves load classification, pure recovery, stale world rebinding, bounded fallback, zero tick/event change, and unknown-field retention.

## Rules for future changes

1. Prefer an exported pure migration/normalization function over an in-place database rewrite.
2. Preserve unknown optional fields unless a documented security boundary requires removal.
3. Never advance simulation time, generate events, resolve a case, or consume a queue item while migrating.
4. Keep migrations deterministic and idempotent: applying the same migration twice must produce the same authority state.
5. Add a legacy fixture, current fixture, corrupt-input fixture, and rollback/recovery assertion before changing a persisted format.
6. Back up a real database before a future schema migration. Do not edit a player database by hand to make a test pass.
7. A future incompatible format requires a separately reviewed schema/version increase; v10.0 contains no such migration.

Browser study data is not a game save. Public review catalogs, build output, replay exports, and release evidence are also not save authorities.
