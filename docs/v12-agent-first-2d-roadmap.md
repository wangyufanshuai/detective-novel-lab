# v12 Agent-first 侦探小镇路线

日期：2026-10-30。性质：基于当前仓库源码、既有验证记录和开源项目对照形成的开发决策。它把 Agent 内核和可玩的 UI 放在美术资产之前；不会删除 v1/v2/v3 Blender 候选，也不把它们当作本阶段的阻塞项。

当前执行范围为 P0/P1，入口 `/town-play/agent-first`。为直接复用已验证的日程和存档，首批地图采用既有河湾世界的广场、旅馆、车站、咖啡馆、旧书店；尚未建立下文的“暴风雪三日”新世界，也未把警务所改名为诊所。实际功能、合同和未闭合门槛见 `agent-first-v1/README.zh-CN.md`；下文 P2–P5 仍为后续路线，不能按 P0/P1 证据宣称完成。

第二轮进入 P2 的规则生活基础：增加明确启用的 72 小时需求/活动策略、直接事件记忆和交谈信任变化。当前功能与新源码验证见 `agent-first-v2/README.zh-CN.md`；它仍不包含完整认知 Agent、模型行为对比、24/100 人负载或案件/小说联动。第一轮证据保留为历史快照。

第三轮增加 `resident-life-proposal.v1` 候选/来源/Referee 层：默认规则模式仍写入同一生活时钟，`offline-agent` 只作为有预算的本地比较臂。当前证据见 `agent-first-v3/README.zh-CN.md` 与 `agent-first-v3/review.json`；没有 live LLM 调用，不能把离线比较称为模型质量验收。

## 决策

主线改为 **Web 优先、Agent 内核优先、2D 俯视探索优先**：

```text
确定性世界核心
  -> 居民观察 / 记忆 / 关系 / 目标
  -> Agent 提案
  -> 权威 Referee 验证
  -> 事件日志与回放
  -> 2D 小镇探索 + 案件本 + Agent 观察面板
  -> 后续可替换的 Blender / GLB / Windows 皮肤
```

第一版画面采用类似《星露谷物语》的轻量俯视模型：瓦片地图、简单角色精灵、少量室内切换、底部工具栏和明确的交互提示。它承担的是“看见人物如何生活、跟随、询问、调查、形成判断”的验证任务。建筑细节、复杂角色建模、真实光照和高模资产不再决定 Agent 版本是否能运行。

这条路线仍然保留用户已经确定的产品特征：古典侦探氛围、角色探索、工具栏、全镇沙盘、案件与小说工作台联动、Windows 下载版的长期目标。Windows 打包在浏览器垂直切片稳定后进行，不提前把工程迁移到 Unity 或 Godot。

## 为什么这样调整

当前仓库已经有 `persistent-town`、`town/runtime`、`town/agent-control`、`population-flow`、`replay-contract`、`replay-executor`、`replay-verifier`、世界包和案件投影。`WorldConsoleSurface`、`TownMapSurface`、`TownPlayClient`、`LivingTown` 也已经提供了地图、居民观察、因果流和运行控制的 UI 基础。继续做高成本房间和街区建模，会反复验证已经存在的模拟能力，却推迟最关键的可玩闭环。

2D 视图的价值是可以很快观察到 Agent 的行为是否真的有意义：居民是否按日程移动，是否记住一次谈话，关系是否改变，事件是否产生后果，玩家是否能在不看内部真相的情况下找到下一步。等这些问题通过后，任何 3D 皮肤都只是替换渲染层和地点表现层。

## Agent 内核目标

### 世界真值和权限

- 世界状态、时间、事件日志、案件真相、证据来源和回放摘要只由引擎拥有。
- Agent 只能产生结构化提案；提案包含 `actionId`、`expectedRevision`、`reason`、`sourceRefs`、目标和置信度。
- Referee 检查权限、空间可达性、时间、资源、关系条件、案件规则和并发 revision，成功后才写入事件日志。
- LLM、React、2D 地图和未来 GLB 场景都不能直接写入死亡、凶手、证据归属或世界时间。
- 玩家投影只返回已观察或已公开的内容；作者/审计投影才能看到完整来源链和隐藏真相。

### 每个居民的最小状态

第一版不追求复杂人格模型，先保证状态能被看懂、能回放：

```text
identity       身份、职业、公开描述
needs          安全、精力、金钱、社交需求
goals          当前目标和优先级
schedule       日程片段与允许的地点
relationships  关系强度、信任、冲突、已知秘密
memory         事件记忆、来源、时间、可信度、遗忘摘要
beliefs        关于人物/地点/案件的可见假设与置信度
plan           下一步行动与失败后的替代行动
```

行动分成三层：

1. **规则层**：走路、工作、吃饭、休息、到达地点和基础社交，不调用 LLM。
2. **Agent 层**：在日程冲突、关系变化、案件压力、突发事件时提出行动计划。
3. **语言层**：把已批准的行动、记忆和公开事实写成对话、手记或小说素材。语言层不能创造新的世界事实。

### 调度和成本

- 2D 渲染每帧只更新画面，不推进世界。
- 世界以游戏分钟或事件触发推进；默认每 5–15 秒批量处理一小组居民。
- 没有重大变化的居民使用规则策略和摘要状态；只有需要重新规划的居民进入 Agent 决策队列。
- LLM 调用必须有预算、超时、缓存、重试和本地规则回退。断网或没有密钥时，游戏仍能用规则策略运行。
- 观察、提案、拒绝、提交、回放和失败原因都进入可审计 receipt，便于比较不同模型。

## 第一个可玩垂直切片

名称暂定为 **雪松山庄：暴风雪三日**。它复用现有雪松山庄叙事气质，但使用轻量地图和简化角色，不等待 Blender 街区完成。

范围建议：

- 1 个 2D 街区地图，约 5 个地点：山庄、车站/道路、咖啡馆、诊所、广场。
- 12 名居民，包含旅馆主人、作家、医生、车站职员、商人、访客和侦探等不同日程。
- 3 个游戏日，1 宗完整案件，6 个可调查对象，4 个公开或可验证证据，2 条可行推理路线。
- 6 个快捷工具：观察、询问、跟随、记录、地图、案件本。
- 玩家从山庄门前出发，可以在地图上行走，靠近人物或地点后只出现一个主要交互。
- 居民离开玩家视野后只显示最后一次公开观察；作者/审计面板才能看到完整轨迹。
- 结案后至少有 3 个可见世界后果，例如居民改变日程、地点开放/关闭、关系变化或新的公开事件。

第一版不做完整种田、饥饿、背包经济、复杂房屋装修、多人联机和高模室内。它只做支撑侦探体验的生活模拟。

## UI 结构

### 主探索界面

- 中央：可平移的 2D 俯视地图，角色、地点、道路和天气组成主要画面。
- 左上：日期、时间、天气和最多一条当前目标。
- 底部：六至八格工具栏，显示当前工具、快捷键和冷却/条件。
- 右下：靠近对象时出现一个交互按钮，写清楚“询问”“观察”或“进入”。
- 右上：地图、案件本、人物观察和设置入口；这些面板按需打开，不常驻遮挡画面。
- 对话：底部短对话框，旁边显示说话者、关系变化和是否记录到案件本。

### 沙盘与 Agent 观察

地图缩小后进入全镇沙盘：

- 只显示玩家已公开或已观察到的人物位置。
- 选中居民后显示公开日程、最近一次观察、关系状态和下一步公开行动。
- 因果流、决策 trace、候选案件和回放属于可折叠的调查/审计面板，不塞进常驻 HUD。
- 作者模式和玩家模式使用不同 API 投影，不能通过前端隐藏按钮绕过权限边界。

### 小说工作台

网页保留 `detective-novel-lab` 的写作入口。案件本可以把已确认的事实、证据和人物关系送入写作桌；写作桌只读取指定的世界版本和披露范围。

桥接记录至少绑定：`worldId`、`worldRevision`、`caseId`、`branchId`、`chapterId`、人物/地点映射、事实来源、首次可知章节和当前稿件依赖的真相版本。改变凶手、时刻、证据或知情范围时创建候选修订，不能静默覆盖已经锁定的案件或稿件。

## 现有代码的复用边界

### 直接复用

- `packages/engine/src/town/runtime.ts`、`persistent-town.ts`、`execution.ts`：世界推进和权威写入。
- `packages/engine/src/town/agent-control.ts`、`population-flow.ts`、`daily-routine.ts`：Agent 提案、居民日程和人口流动。
- `packages/engine/src/town/replay-contract.ts`、`replay-executor.ts`、`replay-verifier.ts`：确定性回放。
- `packages/engine/src/world-case.ts`、`world-causal-trace.ts`、`proof-ledger.ts`：案件来源、因果和证据。
- `app/components/WorldConsoleSurface.tsx`、`TownMapSurface.tsx`、`TownPlayClient.tsx`、`LivingTown.tsx`：地图、居民观察和运行控制。
- `app/components/NovelWorldWorkbench.tsx`、`packages/engine/src/novel-world.ts`、`novel-simulation.ts`：小说工作台和版本边界。

### 新增的薄层

建议新增一个小的探索适配层，而不是再建一套模拟器：

```text
app/town-play/agent-first/
  AgentFirstTown.tsx       2D 主画面
  agent-first.module.css   侦探工具栏和面板样式
  agent-first-map.ts       地图投影与公开角色标记
  agent-first-actions.ts   玩家动作到权威命令的映射

packages/engine/src/town/
  agent-observation.ts     玩家可见观察合同
  agent-intent.ts          提案和拒绝原因合同
  case-bridge.ts           小镇案件到小说章节的版本绑定
```

不要让新的 2D 画面直接读取 runtime 内部对象；它只消费 `player projection` 和 `review projection`。不要为“像星露谷”引入新的独立物理、库存或时间系统。

## 分阶段执行

### P0：冻结内核合同

交付：Agent observation、intent、referee rejection、case bridge 四个合同；明确玩家/作者/审计字段；给每个合同写最小回放和权限测试。

放行条件：相同 seed 和相同输入得到相同 digest；过期 revision、重复 `actionId`、缺少 `sourceRef` 和越权字段都被拒绝；公开投影不包含 hidden truth。

### P1：2D 运行外壳

交付：5 个地点的瓦片地图、可行走角色、时间/天气、进入地点、靠近交互、六格工具栏、案件本空壳。

放行条件：1280×720 和 390×844 都能理解“我在哪、下一步做什么”；角色移动不写数据库，语义动作才提交命令；浏览器实际操作通过。

### P2：12 名居民和三日生活

交付：日程、需求、记忆、关系、公开事件、规则回退策略和 12 名居民的不同工作/社交节奏。

放行条件：至少 5 个 seed 的三日回放稳定；重复率、居民行动覆盖、事件多样性和长跑耗时都有 receipt；没有 LLM 时仍能完成基础循环。

### P3：侦探案件闭环

交付：隐藏真相、局部证词、物证、记忆冲突、案件候选、案件本、理论提交、结案余波。

放行条件：玩家投影不泄漏答案；每条决定性证据可追溯到事件；错误理论有可解释的拒绝原因；至少一条公平可重放路线和一条合法替代路线成立。

### P4：小说桥接

交付：选择世界/案件版本、章节蓝图、可知范围、段落来源、稿件版本和候选修订。

放行条件：同一案件可以生成一条可玩路线和一份短篇候选；改动真相会标记受影响章节和证据，而不会覆盖旧稿。

### P5：美术与 Windows 皮肤

交付：先用 2D 像素/纸片风格完成一套统一 UI，再逐步替换为 Blender/GLB 地标、角色和室内；最后再决定是否需要 Unity/Godot 外壳。

放行条件：替换渲染层不改变 world digest、事件日志、案件本和回放；浏览器和 Windows 包的行为一致；真实目标设备单独记录性能。

## 验收指标

### 内核

- 同 seed、同 package、同命令序列的 canonical digest 一致。
- 提案提交幂等，旧 revision 被拒绝，拒绝原因可读。
- 玩家公开投影不包含凶手、未发现证据、完整居民轨迹或审计 source ids。
- 规则回退在没有 LLM/API 的情况下仍能运行三日切片。

### Agent 行为

- 12 名居民都有可区分的日程和至少一种关系变化。
- 事件不是每 tick 重复同一动作；长跑中保留行动混合、来源链和失败记录。
- 同一事件可在居民记忆、公开事件和案件证据之间保持来源一致。
- LLM 只影响候选意图和语言，不直接改变真值。

### UI

- 新用户在 30 秒内能找到角色、时间、目标和第一个交互。
- 主界面一次只有一个主要行动；地图、案件本、人物观察可以随时返回，不丢位置和镜头。
- 真实浏览器中验证移动、交互、暂停、案件本、错误恢复、窄窗口和无 API fallback。

### 性能

- 2D 首版以稳定 60 fps 为目标；记录真实设备、分辨率、浏览器、帧间隔 p95、加载时间和长跑时间。
- 世界推进和渲染分开测量；LLM 等待不能阻塞渲染线程。
- 先测 12/24/100 居民，再决定是否需要并行化；不把一次截图当作多人性能证明。

## 停止和重规划条件

- 规则回退都无法完成三日闭环时，先修世界规则和事件来源，不增加更多模型或 3D 资产。
- 玩家无法在 30 秒内理解下一步时，先改 HUD 和交互层，不加更多面板。
- 案件不能从证据回放重建时，停止内容扩张，先修 sourceRefs、披露边界和 referee。
- 12 名居民的长跑已经不稳定时，不扩到 100 名居民；先定位重复、饥饿循环、关系爆炸或写入冲突。
- 当 2D 垂直切片通过人工试玩和设备性能后，再恢复 Blender 街区制作；v3 山庄作为地标候选和视觉基准保留。

## 开源参考的取舍

- **Generative Agents / Smallville**：借鉴“环境服务与模拟服务分离、记忆与日程驱动居民”的结构；不直接复制旧 Django/Python 运行时。官方实现是研究型演示，依赖 LLM 和嵌入服务，适合作为认知模块参考。
- **Concordia**：借鉴组件化实体、环境/轮次和 Game Master 处理行动结果的思想；把 Game Master 的裁决职责落实到本项目确定性 Referee，而不是让 LLM 直接拥有世界真值。
- **Project Sid**：借鉴小规模可观察社会先行、角色/关系/治理/文化事件都写入持久状态的路线；不把 1,000 名 Agent 的研究结果当作首版性能目标。
- **AgentSociety 2**：借鉴“假设 → 社会模拟 → 干预 → 分析”的实验工作流；只吸收实验与回放边界，不把大规模城市数据和商业目录带入侦探小镇。
- **Project Genesis / AgentCiv**：借鉴“Agent 只提案，确定性引擎裁决”的硬边界，以及用小规模实验测量涌现；不把“涌现”当成没有指标的宣传词。

以上项目的代码、数据和资产许可证要逐项核对，研究仓库不能自动视为可商用资产。我们的原创 Agent 内核、案件内容、地图和 UI 仍需单独维护来源账本。

## 最终建议

先做一个能运行三日、能观察 12 名居民、能完成一宗公平案件的 2D 侦探小镇。只要这个切片让你愿意反复观察居民、跟踪关系、翻案件本和阅读世界余波，项目的核心就成立了；之后再把它换成更好的角色、建筑、Blender/GLB 地标和 Windows 外壳。现在继续堆高模，会让美术成本先于产品验证，无法回答你真正想要的“Agent 是否真的活起来”。
